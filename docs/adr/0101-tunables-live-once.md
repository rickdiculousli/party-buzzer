# Motion tunables live once in CSS; cue numbers live in recipes

Every signature motion number lives in the `anim:tunables` block of `client/style.css`, the one place the motion harness reaches and writes back. A few tunables also pace script: `--mark-stagger` spaces both the timeline marks and their sounds (`markGap`), since two staggers would drift apart on the first tweak, and `--type-chunk`, `--verdict-hold` and `--penalty-dwell` pace timers in `Spoken.tsx` and `useReveal.ts` rather than keyframes but stay tunables so the harness reaches them. Script reads them with `tune()`.

- `TUNE` holds exactly one JavaScript fallback per tunable, for when the DOM has none; fallbacks are never restated at call sites. Runtime cannot notice a fallback drifting (it fires only when the property is missing), so `client/tunables.test.ts` compares every entry with its declaration inside the `anim:tunables` block, parsed the way the browser value is. Only that block counts, because a tunable declared elsewhere is one the harness cannot write. The one exception is `--finale-build-dur` on `.board__finale-flash`, held equal to `FINALE_SCHEDULE.build`.
- `parseTune` converts a trailing `s` to milliseconds because the production CSS minifier rewrites `1000ms` as `1s`: a bare `parseFloat` would cut a one-second sound to one millisecond in the build while dev stayed correct. Unitless dials pass straight through.
- A cue's gain, delay, envelope and trim are fields on its recipe layers in `client/cues.ts`, never custom properties: a parallel CSS copy would give one value two homes and the recipe path would silently ignore it. `--mark-stagger` is the only cue timing kept in CSS, because it is shared with the picture.

Where: `client/style.css` (`anim:tunables`), `client/sound.ts` (`TUNE`, `tune`, `parseTune`, `play`, `markGap`), `client/cues.ts` (`RECIPES`), `client/Spoken.tsx`, `client/useReveal.ts`, `client/tunables.test.ts`, `client/sound.test.ts`, `shared/wall.ts` (`FINALE_SCHEDULE`)
